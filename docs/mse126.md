# MLP-only NVFP4 exhaustive block-scale search

This candidate keeps NVFP4 execution on every unit and changes only the MLP
gate/up/down encoding in layers 0–3. It holds each Linear's max-calibrated tensor
scale fixed, searches all 126 positive finite E4M3 block-scale values, and minimizes
float64 weight reconstruction loss. RTN wins ties. Encoding uses 64-row chunks
and reads only that Linear's canonical BF16 weights; it requires no calibration
input, GPU, network, persistent cache or cross-tensor transformation.

The four-layer scope matches the real-weight evidence and limits CPU build cost.
It does not add GDN Q4_K to the previously merged #15 recipe. The hypothesis is
that better NVFP4 weight bytes can improve fidelity while retaining native FP4
prefill. Unchanged storage format does **not** establish unchanged throughput.

## Evidence and limits

On canonical BF16 shard 1, SHA256
`ba0ce20aae489ad196733da5064bcdf159a1fe84f53336648196e1ebb7751b1c`,
16 evenly spaced rows of each of the 12 language MLP tensors in layers 0–3 were
encoded using each complete tensor's amax. Reconstruction SSE decreased
25.98–27.39% vs RTN and 14.74–16.01% vs PR #3's five clipping ratios. Repeat
encoding produced identical bytes. These are sampled **weight reconstruction**
results, not activation error, model fidelity, task accuracy or inference speed.

The evaluator-style synthetic probe (seed 74, 13,872 comparable bytes) had
51.94% identical bytes to RTN and 59.12% to the original `mse_clip@v1` from PR #3
head `032d629227bbcf4d94fe2d45ae4ced839e0bd9ae`, below the 99% same-encoder
threshold. A trusted evaluator must independently repeat its own probe and
checkpoint-byte comparisons; a different name alone does not establish novelty.

Tests cover byte repeatability, chunk independence with a tensor-wide amax,
per-block loss against RTN, zero/invalid inputs, two complete tiny checkpoint
builds, audit replay, preservation of tensors outside MLP, rejection of non-MLP
assignment, and detection of a modified encoded byte.

Full-model source audit, build time, public section-balanced RP-KL, task guards,
long-context correctness, private holdout, peak memory and throughput have **not**
been measured. Exhaustive NumPy encoding can be expensive on full tensors; the
candidate remains a draft until the full build and fixed-runtime development
checks are feasible. No reward or performance gain is claimed.
